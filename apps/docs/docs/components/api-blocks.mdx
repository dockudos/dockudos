These three components are the building blocks of a hand-written API reference. `Endpoint` names the call,
`ParamField` lists what goes in, and `ResponseField` lists what comes out.

<Endpoint method="POST" path="/v1/users" baseUrl="https://api.acme.dev" />

<ParamField name="email" type="string" location="body" required>
  The user's email address.
</ParamField>
<ParamField
  name="role"
  type="'admin' | 'member'"
  location="body"
  default="'member'"
>
  Access level of the new user.
</ParamField>
<ParamField name="X-Request-Id" type="string" location="header">
  Optional. Echoed back in the response so you can match logs.
</ParamField>

<ResponseField name="id" type="string">
  The id of the new user.
</ResponseField>
<ResponseField name="created_at" type="string (ISO 8601)">
  When the user was created.
</ResponseField>

```mdx
<Endpoint method="POST" path="/v1/users" baseUrl="https://api.acme.dev" />

<ParamField name="email" type="string" location="body" required>
  The user's email address.
</ParamField>

<ResponseField name="id" type="string">
  The id of the new user.
</ResponseField>
```

## Endpoint

An HTTP method and a path on one line.

| Method            | Color |
| ----------------- | ----- |
| `GET`             | blue  |
| `POST`            | green |
| `PUT`, `PATCH`    | amber |
| `DELETE`          | red   |
| `HEAD`, `OPTIONS` | gray  |

Color helps people scan, but the method name is always written out, so it is never the only signal. An unknown method is
shown as `GET`. Keep `{placeholders}` in the path as written, for example `/v1/users/{id}`; `baseUrl` is shown dimmed in front.

<Endpoint method="GET" path="/v1/users/{id}" />
<Endpoint
  method="DELETE"
  path="/v1/users/{id}"
  baseUrl="https://api.acme.dev"
/>

## ParamField

One documented parameter: its name, then labels for its type, location, whether it is required and its default, then a
description underneath. The description is ordinary content, so it can have code, lists and links, and even a nested
[Expandable](./layout-blocks.mdx) for the properties of an object.

<ParamField name="filter" type="object" location="query">
  Narrow the results.

<Expandable title="Properties">
  <ParamField name="status" type="'active' | 'closed'">
    Only items in this state.
  </ParamField>
  <ParamField name="owner" type="string">
    Only items owned by this id.
  </ParamField>
</Expandable>
</ParamField>

```mdx
<ParamField name="filter" type="object" location="query">
  Narrow the results.

<Expandable title="Properties">
  <ParamField name="status" type="'active' | 'closed'">
    Only items in this state.
  </ParamField>
</Expandable>
</ParamField>
```

It is not only for HTTP. Use it for the arguments of a function, the options of a CLI command or the keys of a config
file; `location` can be any word, such as `flag` or `env`.

## ResponseField

The same as `ParamField`, minus `required` and `location`, for the fields of a response or a return value. It takes `name`,
`type`, `default` and children.

## Putting it together

A typical API page has an `Endpoint`, a "Parameters" section of `ParamField`s, a "Response" section of `ResponseField`s,
and a [Panel](./panel-and-examples.mdx) with the request and response examples pinned beside the text. Generated
reference pages from an OpenAPI file are planned for a later release and will use these same components.
